# WebDAV-MD 자동 오류·기능 점검 도구 기획

## 1. 목적

앱을 수정한 뒤 사람이 모든 버튼을 다시 눌러보지 않아도, 변경으로 인해 기존 기능이 깨졌는지를 한 번의 명령으로 확인한다.

이 도구의 목표는 단순히 문법 오류를 찾는 것이 아니다. 다음 네 가지 질문에 자동으로 답해야 한다.

1. 코드 자체에 명백한 오류가 없는가?
2. 데이터 저장, 이동, 복구 같은 핵심 로직이 정상인가?
3. 사용자가 화면에서 주요 작업을 실제로 완료할 수 있는가?
4. 배포해도 되는 상태인가?

도구의 임시 이름은 **App Doctor**로 한다.

## 2. 완료 기준

아래 조건을 모두 만족할 때만 업데이트를 배포 가능한 상태로 판정한다.

- `npm run check` 한 번으로 모든 자동 점검이 실행된다.
- 실패 시 "어느 기능 / 어느 단계 / 기대 결과 / 실제 결과"가 표시된다.
- 핵심 기능 테스트 실패 시 빌드와 배포가 자동으로 중단된다.
- 브라우저 테스트 실패 시 스크린샷, 콘솔 오류, 네트워크 실패 내역이 남는다.
- 외부 WebDAV·AI 서비스가 없어도 대부분의 테스트를 재현할 수 있다.
- 외부 서비스가 필요한 테스트는 별도 실환경 점검으로 분리한다.
- 사람이 확인할 항목은 자동화 불가능한 시각·감각 품질에 한정한다.

## 3. 현재 상태와 문제

현재 프로젝트에는 좋은 출발점이 이미 있다.

- Node 기본 테스트 기반의 테스트 파일 37개와 약 136개 테스트가 있다.
- WebDAV CRUD/이동, 백업, AI 응답 정리, 편집기, A4 페이지 등 주요 로직 일부가 테스트된다.
- ESLint와 Vite 빌드가 설정되어 있다.
- `tsconfig.json`은 `strict`이지만 전체 소스 230개 중 JavaScript가 207개, JSX가 21개이고 TypeScript/TSX는 2개뿐이다.

현재의 주요 공백은 다음과 같다.

- `package.json`에 통합 테스트 및 타입 검사 명령이 없다.
- TypeScript 컴파일러가 설치되어 있지 않아 `strict` 설정이 품질 관문으로 작동하지 않는다.
- 실제 브라우저에서 로그인 → 파일 열기 → 편집 → 저장처럼 이어지는 사용자 흐름 테스트가 없다.
- GitHub Pages 배포 작업은 빌드만 확인하며 테스트·린트 실패를 배포 차단 조건으로 쓰지 않는다.
- 일부 테스트는 큰 소스 파일에서 문자열로 함수 일부를 잘라 검사하므로 화면 연결이 끊겨도 통과할 수 있다.
- 기능 목록과 테스트의 대응표가 없어 새 기능이 테스트에서 빠져도 알아채기 어렵다.

## 4. 도구 구조

App Doctor는 빠른 검사부터 실제 사용자 흐름까지 5개 층으로 구성한다.

| 단계 | 검사 내용 | 권장 도구 | 실행 시점 | 실패 시 |
|---|---|---|---|---|
| L1 정적 검사 | 문법, 미사용 코드, React Hook, 타입 | ESLint, TypeScript | 저장/커밋 전 | 즉시 수정 |
| L2 단위 검사 | 함수, 변환, 경계값, 오류 처리 | Node Test | 모든 변경 | 병합 차단 |
| L3 통합 검사 | WebDAV 요청, 저장소, 백업, 브리지 연결 | Node Test + 가짜 서버 | 모든 변경 | 병합 차단 |
| L4 사용자 흐름 | 클릭, 입력, 저장, 새로고침, 화면 전환 | Playwright | PR/배포 전 | 배포 차단 |
| L5 실환경 점검 | 실제 NAS, AI API, 이메일 등 | 별도 smoke 작업 | 선택/정기 실행 | 경고 또는 배포 보류 |

### 실행 명령 설계

```text
npm run check:fast     L1 + L2, 개발 중 수시 실행
npm run check          L1 + L2 + L3 + 빌드, 커밋 전 실행
npm run check:e2e      L4 브라우저 핵심 흐름 실행
npm run check:release  L1~L4 전체 실행, 배포 전 필수
npm run check:live     L5 실환경 점검, 자격 증명 있을 때만 실행
```

`check:release` 결과는 성공/실패 코드뿐 아니라 HTML 보고서로도 만든다. 첫 화면에는 전체 통과율보다 **배포 가능 / 배포 금지**를 크게 보여준다.

## 5. 기능 체크리스트

체크리스트는 문서에만 두지 않고 `tests/feature-matrix` 같은 기계 판독 가능한 파일로 관리한다. 모든 핵심 기능에는 담당 테스트 ID가 있어야 한다.

### P0: 반드시 자동화하고 실패 시 배포 차단

- [ ] 앱이 빈 화면 없이 시작된다.
- [ ] 로그인 세션이 저장되고 새로고침 후 복구된다.
- [ ] WebDAV 연결 성공·실패가 정확히 표시된다.
- [ ] 폴더 목록을 읽고 이동할 수 있다.
- [ ] 새 문서를 만들고 내용 입력 후 저장할 수 있다.
- [ ] 저장한 문서를 다시 열었을 때 내용이 동일하다.
- [ ] 파일 이름 변경, 이동, 삭제가 실제 결과까지 검증된다.
- [ ] 충돌 또는 네트워크 실패 시 원본 데이터가 보존된다.
- [ ] 자동 저장과 시작 시 문서 복구가 동작한다.
- [ ] 편집 모드와 미리보기 모드를 전환할 수 있다.
- [ ] JavaScript 런타임 오류와 처리되지 않은 Promise 오류가 없다.
- [ ] 빌드 결과의 시작 페이지와 필수 정적 자산이 존재한다.

### P1: 주요 기능, PR에서 자동 검사

- [ ] Markdown 굵게, 목록 들여쓰기, 코드, 이미지, Mermaid가 정상 렌더링된다.
- [ ] A4/긴 문서 변환에서 내용과 페이지 설정이 보존된다.
- [ ] 미니 미리보기, 전체화면, 창/패널 크기 변경이 동작한다.
- [ ] 백업 생성, 목록 조회, 복원 실패 처리 흐름이 동작한다.
- [ ] 공유 링크/공유 화면이 올바른 문서를 표시한다.
- [ ] 설정 변경이 저장되고 재시작 후 복구된다.
- [ ] AI 설정, 모델 목록, 응답 삽입이 가짜 API 응답에서 동작한다.
- [ ] 모바일 화면 크기에서 핵심 편집과 저장을 수행할 수 있다.
- [ ] 키보드 단축키가 입력 중인 텍스트를 훼손하지 않는다.

### P2: 실환경 또는 수동 보조 검사

- [ ] 실제 NAS에서 대용량 파일과 깊은 폴더를 처리한다.
- [ ] 실제 AI 제공자별 응답·스트리밍이 동작한다.
- [ ] 실제 백업 이메일이 도착한다.
- [ ] 주요 브라우저 및 모바일 실기기에서 레이아웃이 자연스럽다.
- [ ] 긴 문서 편집 성능과 메모리 사용이 허용 범위다.

## 6. 사용자 흐름 테스트 설계

버튼 하나씩 테스트하기보다 사용자가 목적을 달성하는 흐름을 테스트한다.

### 시나리오 A: 문서 생명주기

1. 테스트 WebDAV로 로그인한다.
2. 폴더를 생성한다.
3. Markdown 문서를 생성하고 한글·목록·이미지를 입력한다.
4. 저장 후 새로고침한다.
5. 같은 문서를 다시 열어 내용 일치를 확인한다.
6. 이름을 변경하고 다른 폴더로 이동한다.
7. 삭제 후 목록에서 사라졌는지 확인한다.

### 시나리오 B: 실패해도 데이터 보존

1. 기존 문서를 연다.
2. 저장 도중 테스트 서버가 500 또는 연결 끊김을 반환한다.
3. 성공 알림이 나오지 않는지 확인한다.
4. 원본 파일과 편집 중 내용이 남아 있는지 확인한다.
5. 연결 복구 후 재시도하여 정상 저장되는지 확인한다.

### 시나리오 C: 편집·미리보기

1. Markdown 샘플 문서를 연다.
2. 편집 명령과 단축키를 수행한다.
3. 미리보기와 A4 화면으로 전환한다.
4. 텍스트 손실, 브라우저 콘솔 오류, 깨진 이미지가 없는지 확인한다.

### 시나리오 D: 설정 복구

1. 주요 설정과 기능 토글을 바꾼다.
2. 앱을 완전히 새로고침한다.
3. 설정과 화면 상태가 복구되는지 확인한다.
4. 저장 데이터가 손상된 경우 안전한 기본값으로 시작하는지 확인한다.

## 7. 외부 서비스 테스트 전략

자동 점검이 NAS나 AI 서비스 상태 때문에 흔들리면 신뢰를 잃는다. 따라서 두 종류로 분리한다.

- **가짜 환경 테스트:** 로컬 WebDAV/API 서버가 성공, 인증 실패, 충돌, 느린 응답, 연결 끊김을 재현한다. 모든 PR에서 실행한다.
- **실환경 smoke 테스트:** 비밀키가 설정된 전용 테스트 계정과 폴더만 사용한다. 수동 요청 또는 정기 실행하며 실제 사용자 데이터에는 접근하지 않는다.

테스트 데이터는 각 실행마다 고유한 폴더를 사용하고, 종료 시 그 폴더만 정리한다. 삭제 전 경로가 테스트 전용 루트 안인지 반드시 검사한다.

## 8. TypeScript 수준의 오류 방지 계획

전체를 한 번에 TypeScript로 바꾸지 않는다. 변경 위험을 줄이기 위해 점진적으로 적용한다.

1. TypeScript를 개발 의존성에 추가하고 `tsc --noEmit`을 품질 관문에 넣는다.
2. 우선 JavaScript에도 `checkJs`와 JSDoc 타입을 적용할 수 있는 범위를 정한다.
3. WebDAV 경로, 파일 메타데이터, 저장 결과, 설정 객체처럼 여러 모듈이 공유하는 타입부터 정의한다.
4. 새 파일은 원칙적으로 TypeScript로 작성한다.
5. 자주 깨지는 핵심 모듈부터 `.js/.jsx`를 `.ts/.tsx`로 전환한다.
6. 타입 오류를 `any`로 숨기지 않고 외부 입력 경계에서 검증한다.

우선 전환 대상은 WebDAV 작업 계층, 설정/저장 데이터, 앱과 MDPro 사이 메시지 브리지, 백업 API 순서가 적합하다.

## 9. 실패 보고서 형식

실패 메시지는 개발자가 바로 재현할 수 있어야 한다.

```text
[배포 금지] DOC-001 문서 저장 후 재열기
실패 단계: 저장 버튼 클릭 후 PUT 응답 확인
기대 결과: /doctor/run-123/note.md 내용이 입력값과 같음
실제 결과: 서버에는 이전 내용이 남아 있음
브라우저 오류: TypeError ...
첨부: screenshot.png, trace.zip, console.log, network.json
재실행: npm run check:e2e -- --grep DOC-001
```

불안정하게 가끔 실패하는 테스트는 단순 재시도로 숨기지 않는다. 격리 목록에 넣고 담당자·원인·해결 기한을 기록하며, P0 테스트는 격리를 허용하지 않는다.

## 10. CI/CD 품질 관문

권장 흐름은 다음과 같다.

```text
코드 변경
  → 빠른 검사(L1~L2)
  → PR 전체 검사(L1~L4)
  → 품질 관문 통과
  → 빌드
  → 배포
  → 선택적 실환경 smoke(L5)
```

현재 GitHub Pages 작업의 배포 앞에 `check:release`를 추가한다. 다음 항목 중 하나라도 실패하면 배포하지 않는다.

- 타입 검사
- ESLint
- 단위/통합 테스트
- P0 브라우저 테스트
- 프로덕션 빌드
- 빌드 산출물 smoke 검사

## 11. 도입 단계

### 0단계: 기준선과 기능 지도

- 모든 기능을 P0/P1/P2로 분류한다.
- 기존 테스트를 기능 ID와 연결한다.
- 현재 오류는 별도 기준선으로 기록하고 새 오류와 구분한다.

완료 조건: 핵심 기능 100%가 체크리스트에 있고 누락된 자동 테스트가 보인다.

### 1단계: 한 명령 품질 검사

- 테스트, 린트, 타입 검사, 빌드 명령을 통합한다.
- 로컬과 CI가 같은 명령을 실행하게 한다.
- 읽기 쉬운 콘솔 요약과 실패 코드를 제공한다.

완료 조건: `npm run check` 결과만 보고 변경의 기본 안전성을 판단할 수 있다.

### 2단계: 핵심 E2E 4개

- Playwright와 테스트 전용 가짜 WebDAV/API 서버를 도입한다.
- 위 A~D 시나리오를 자동화한다.
- 오류 시 trace, 스크린샷, 콘솔, 네트워크 로그를 저장한다.

완료 조건: P0 핵심 흐름이 사람의 클릭 없이 재현된다.

### 3단계: 배포 차단

- PR과 main 배포 앞에 전체 검사를 연결한다.
- 기능 매트릭스에 테스트가 없는 P0 기능이 생기면 검사 실패로 처리한다.
- 결과 보고서를 CI 산출물로 보관한다.

완료 조건: 검사 실패 버전은 자동 배포될 수 없다.

### 4단계: 확대와 안정화

- P1 흐름, 모바일 뷰포트, 접근성, 성능 기준을 추가한다.
- 실제 NAS·AI·메일 smoke 검사를 별도 운영한다.
- 반복 발생 오류는 반드시 재현 테스트를 먼저 추가하는 규칙을 정착시킨다.

## 12. 운영 규칙

- 버그를 수정할 때는 같은 버그가 다시 생기면 실패하는 테스트를 함께 추가한다.
- 기능을 추가할 때는 기능 매트릭스와 테스트 ID를 함께 추가한다.
- 화면 텍스트나 CSS 선택자보다 접근 가능한 역할, 라벨, 안정적인 테스트 ID를 사용한다.
- 테스트는 실행 순서에 의존하지 않고 독립적으로 실행 가능해야 한다.
- 스냅샷만으로 기능 성공을 판정하지 않고 저장 결과나 화면 상태를 명시적으로 검증한다.
- 테스트 코드도 제품 코드와 같이 리뷰한다.
- 테스트 실행이 느려지면 삭제하지 않고 fast/full 그룹으로 나눈다.

## 13. 1차 구현 범위 제안

첫 구현에서는 범위를 작게 고정한다.

1. `test`, `typecheck`, `check`, `check:release` 명령 추가
2. TypeScript 검사 활성화 및 현재 오류 기준선 정리
3. Playwright 설치와 테스트 서버 구성
4. 앱 시작, 문서 생명주기, 실패 시 데이터 보존, 설정 복구의 P0 E2E 4개 작성
5. 기능 매트릭스와 HTML/CI 결과 보고서 추가
6. GitHub Pages 배포 전에 `check:release` 실행

이 1차 범위가 끝나면 이후 기능은 체크리스트에 등록되지 않거나 자동 테스트 없이 배포되는 것을 구조적으로 막을 수 있다.
